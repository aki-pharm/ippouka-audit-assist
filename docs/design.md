## 0. ひとことで言うと

一包化の1包目を監査するとき、薬剤師が「この白い錠剤はどの薬か」を**自分の目で**すぐ判断できるように、
処方箋から「朝・昼・夕の袋に入るはずの錠剤」を、添付文書由来の**刻印・形・色・大きさつきのイラスト**で並べて見せるスマホWebアプリ。

- 判断するのは薬剤師。アプリは「調べる手間を減らす」道具。
- カメラに錠剤を判定させない（理由は §2.3）。
- Claudeは「添付文書PDFからの外観情報の抽出」と「処方箋写真の読み取り」に使い、どちらも**人が確認してから**使う。

---

## 1. 用語

| 用語 | 意味 |
|---|---|
| 一包化 | 服用時点（朝・昼・夕など）ごとに複数の薬を1つの袋にまとめること |
| 監査 | 調剤された薬が処方どおりかを薬剤師が確認する工程 |
| 1包目 | 一包化された袋のうち最初の1袋。ここを確認すれば残りは「1包目と同じか」を見るだけになる |
| 刻印（識別コード） | 錠剤に刻まれた文字・記号。添付文書の「性状」欄に載る |
| 一包化区分 | その薬を一包化の袋に入れるか、別包（PTPのまま等）にするかの施設ルール |
| 分包方法 | カセット（分包機に常備）か手巻き（PTPから出して手で入れる）か |
| 採用品 | その施設が実際に在庫している製品（一般名処方はこれに置き換えて表示する） |
| マスタ | 薬ごとの外観・添付文書情報をまとめたデータ |

## 2. 背景と設計思想

### 2.1 課題
- 1包目の監査では、処方箋と袋の中身を見比べて「処方どおりか」を確認する。ここに一番時間がかかる。
- 新しい薬は錠剤名が印字されていて分かりやすいが、古い薬は白い錠剤が多く、刻印を覚えていないと判別できない。
- 同じ大きさ・同じ色の白い錠剤が並ぶと、ベテランでもしんどい。分からなければ添付文書を1つずつ調べている。
- 新人・応援の薬剤師は見慣れない薬が多く、監査の質が個人の経験に依存する。
- 頻度は低いが見逃したときの危害が最大のミス＝「似た見た目の違う薬が入っている」。

### 2.2 既存手段との違い
- 刻印チェック専用機は大型・高価で、使える施設が限られる。
- 本作品は、身近なスマホで、どの施設でも使える形を目指す。
- デモ・資料で他社製品の精度に触れたり批判したりしない。

### 2.3 カメラに判定させない理由（設計の核）
- 撮影技術・撮り方で精度がばらつく。錠剤の裏表で刻印が見えないこともある。
- 同じ大きさ・色の白い錠剤は、カメラ判定では全部「要確認」になり実用にならなかった（過去の経験）。
- だから「薬剤師が自分で判断できる材料」を見やすく出すことに集中する。
- これは禁止例（画像解析ツール・医療アドバイスAI）を避ける意味でも一貫している。

### 2.4 ベテランの監査手順をそのまま画面にする
ベテランは頭の中で「この処方なら朝の袋にはこれとこれが入るはず。あの白い丸いのは刻印○○のはず」と組み立ててから袋を見る。
その頭の中の組み立てを画面に出すのが本作品。だから画面の流れ＝監査手順の順番にする。

### 2.5 やらないこと（明記）
- 錠剤画像の自動判定・照合（カメラでの✅/⚠️判定も今回は作らない。§9 参照）
- 用法用量の妥当性判断、相互作用チェック、服薬指導など医療アドバイスにあたる出力
- 半錠、散剤、カプセル、外用薬、注射薬
- 患者情報の取り扱い（撮影ガイドで薬剤欄だけを写し、画像は保存しない）

## 3. 利用者と利用シーン

- 利用者：病院・薬局の調剤室で一包化の監査をする薬剤師（特に新人・応援・ローテーション）
- 端末：自分のスマホのブラウザ（iPhone Safari / Android Chrome）。アプリのインストール不要。
- 場面：監査台で処方箋と1包目を前にしている。片手でスマホ、片手で袋。
- 制約：手袋をしていることがある → ボタンは大きく、入力は最小限、タップ数を減らす。

## 4. 画面の流れ（ユーザーストーリー）

```
[0 ログイン] 共通パスコード入力（公開URLの保護）
    ↓
[1 処方箋を撮る] 薬剤欄だけが入るガイド枠つきカメラ
    ↓
[2 読み取り結果の確認] 薬・規格・用法・錠数の表（編集できる）＋ 検算結果
    ↓
[3 入れる／入れないを選ぶ] 施設ルールを初期値に、処方ごとに手で変更
    ↓
[4 出来上がりイメージ図] 朝・昼・夕（必要なら眠前）の袋ごとに錠剤イラストを並べる  ← 主役
    ↓
[5 添付文書を開く] 各薬のボタンから出典PDF／マスタ登録情報へ
    ↓
[6 1包目と見比べる（任意）] 1包目を撮って、イメージ図と上下に並べる
```

### 画面ごとの仕様

#### 画面0：パスコード
- 共通パスコード1つ。合っていればCookieを発行し、以後の画面とAPIを許可する。
- 目的は「他人にAPIクレジットを使われないこと」。個人認証ではない。
- 動画にはパスコード入力の瞬間を映さない。

#### 画面1：処方箋の撮影
- `<input type="file" accept="image/*" capture="environment">` でスマホのカメラを起動（最も互換性が高い方法）。
- 「サンプルで試す」ボタン：アプリに同梱した架空の処方箋画像を読み込む（デモ・動作確認用。読み取りは本物を動かす）。
- 撮影前の案内：「薬剤情報の欄だけを写してください。患者情報の欄は入れないでください」「文字が横にならない向きで」＋枠の見本画像。2ページ目があれば「もう1枚撮る」。
- 撮った画像はブラウザ内で長辺1600px程度に縮小してから送信する（通信量・コスト・個人情報の両面で有利）。
- サーバは画像を保存しない。ログにも残さない。

#### 画面2：読み取り結果の確認
- Claudeが返した構造化データを表で表示。各行：薬剤名（処方どおりの表記）／規格／1回量／1日回数／1日量／用法（服用時点）／日数／マスタの対応品。
- **すべてのセルを手で直せる**。読み取りは下書きであり、確定するのは薬剤師。
- 検算：`1回量 × 1日回数 = 1日量` が成り立たない行、用法から服用時点が決まらない行、マスタに該当がない行を黄色で示す。
  - 表現は「読み取り値が一致しません」「マスタに該当がありません」。処方の是非には触れない（§8 言葉づかい）。
- 一般名処方は、マスタの「採用品」に置き換えた製品名を併記する。候補が複数あれば選ばせる。
- 「この内容で進む」ボタンで確定。

#### 画面3：入れる／入れないの選択
- 行ごとにトグル。初期値の決め方：**処方箋の指示（別包／一包化）＞ マスタの一包化区分（施設ルール）**。錠剤以外（カプセル等）は「対象外」として別枠。
- 初期値から変えた行は色と「変更」バッジで目立たせる（監査者に「ここは今回特別」と伝えるため）。
- 「入れない」にした薬は、イメージ図では袋の外に「別包」として小さく表示する（存在を忘れさせない）。

#### 画面4：出来上がりイメージ図（主役）
- 服用時点（朝・昼・夕）ごとに1つの「袋」カードを横並び（スマホでは横スクロール or 縦積み）。袋の見出しに錠数合計。
- 袋の中に錠剤イラスト（SVG）を並べる。錠剤1個＝1イラスト（1回2錠なら2つ描く）。
- イラストの要素：形（円・楕円・長円・その他）、色（マスタの色名→表示色）、大きさ（長径・短径を同じ縮尺で描く。基準は 1mm = 一定px）、刻印（表）を錠剤の上に文字で、刻印（裏）はその下に小さく、割線があれば線。
- 並び順：処方箋の記載順（監査は処方箋を上から見ていくため）。余裕があれば「大きさ順」に切り替えられるようにする。
- **似た外観の注意表示**：同じ袋の中で「形が同じ・色が同じ・長径の差が1.0mm以内」の組があれば、その組の錠剤に同じ色のバッジ（例：Ⓐ）を付け、「⚠ 見分け注意：Ⓐは刻印で区別」の帯を出して刻印を強調表示する。記載順で離れていても対応が分かる。ルールで判定し、AIは使わない。これが「似た見た目の違う薬」ミスへの直接の対策。
- 錠剤をタップすると画面5の情報カードが開く。各錠剤の下に「添付文書を開く」リンクを置き、カードを開かずに一発でPDF（該当ページ）へ飛べる。URL未登録の薬は「PMDAで検索」。
- 刻印が「未確認」の薬は、刻印欄に「未確認」と明示し、イラストの枠を点線にする。「なし」はそのまま刻印なしで描く。

#### 画面5：添付文書・登録情報
- 情報カード：薬剤名／一般名／規格／刻印（表・裏）／色／形／大きさ／一包化区分／分包方法／添付文書の改訂日／マスタ確認日・確認者（イニシャル等）。
- 「添付文書の記載（抜粋）」：抽出の根拠になった性状の一文（source_quote）をそのまま表示し、改訂年月・ページ番号・マスタ確認者と確認日を並べる。刻印が本当に正しいかを、その場で情報源と突き合わせられるようにする。
- ボタン：「添付文書（PDF）を開いて確かめる」→ 出典URL（＋ `#page=N` で該当ページ）を新しいタブで開く。PDFは外部サイトのものをそのまま見せる。
- AIによる要約や用法用量の説明はしない。**情報源をそのまま見せる**。

#### 画面6：1包目との見比べ（任意ステップ）
- 1包目を撮影（撮り方の案内：錠剤を重ねない、無地の背景、反射に注意）。
- 画面上部にイメージ図、下部に写真。スマホでは上下に並べ、指でスクロール／ピンチ拡大できる。
- 画像処理はしない。「見比べる場」を提供するだけ。
- 現場では実物を手に持っているので、このステップは**省略できる**。記録を残したい施設向けの位置づけ。

## 5. 医薬品マスタ

### 5.1 考え方
- 添付文書PDFからClaudeが外観情報を抜き出し、**必ず人が確認してから**マスタに入れる。
- 読めなかった項目は空欄ではなく「未確認」にする。刻印の「なし」と「未確認」は別の値。
- 添付文書PDFそのものは公開リポジトリに入れない。出典URLだけ持つ。
- 画面・資料に病院名は出さない。「よく使われる薬」として扱う。

### 5.2 項目

| 項目 | 型 | 説明 |
|---|---|---|
| id | 文字列 | 内部ID（例：`amlodipine-5-xx`） |
| brand_name | 文字列 | 製品名（販売名） |
| generic_name | 文字列 | 一般名 |
| strength | 文字列 | 規格（例：`5mg`） |
| imprint_front | 文字列 | 刻印（表）。値は文字列／`なし`／`未確認` |
| imprint_back | 文字列 | 刻印（裏）。同上 |
| imprint_note | 文字列 | 補足（社名マーク、割線の有無など） |
| color | 文字列 | 色名（白／白〜微黄白／淡黄／淡赤／…） |
| color_hex | 文字列 | 表示用の色（人が決める。例：`#F5F5F0`） |
| shape | 列挙 | `round` / `oval` / `oblong` / `other` |
| size_long_mm | 数値 | 長径（円形なら直径） |
| size_short_mm | 数値 | 短径（円形なら長径と同じ） |
| thickness_mm | 数値 | 厚さ（任意） |
| score_line | 真偽 | 割線の有無 |
| pack_rule | 列挙 | 一包化区分：`include` / `exclude`（施設ルール初期値） |
| pack_rule_reason | 文字列 | 除外理由（例：下剤のため頓用扱い、吸湿性）。表示用 |
| fill_method | 列挙 | `cassette` / `manual`（分包方法） |
| adopted | 真偽 | 採用品か（一般名処方の置き換え先になるか） |
| source_url | 文字列 | 添付文書の出典URL（PMDA） |
| source_revision | 文字列 | 添付文書の改訂年月 |
| source_page | 数値 | 性状が載っているPDFのページ番号（リンクで直接開く） |
| source_quote | 文字列 | 抽出の根拠となった添付文書の文言（確認を楽にするため） |
| verified_by | 文字列 | 確認者（イニシャル） |
| verified_at | 日付 | 確認日 |
| status | 列挙 | `draft`（抽出直後）/ `verified`（人が確認済み） |

- 保存形式：`data/master.json`（配列）。スプレッドシートで編集しやすいよう `data/master.csv` との相互変換スクリプトも用意する。
- `status: draft` の薬は、アプリでは「未確認（マスタ）」の帯つきで表示し、デモには使わない。

### 5.3 施設ルール
- 一包化区分と分包方法はマスタの行に持つ（＝施設ごとにマスタを持つ設計）。
- 入れる／入れないの決め方（優先順。上が勝つ）：
  1. 処方箋の行コメント「別包（ヒート包装）」「PTP」→ 入れない
  2. 処方箋末尾の緑字「一包化」指示（例：「○○も含めて一包化」）→ 施設ルールで外す薬も含めて全部入れる
  3. 施設ルール（例：下剤、アスパラカリウムはPTPのまま）→ 入れない
  4. それ以外 → 入れる
  - 薬剤師の手での変更は、この結果の上からさらに上書きできる（変更は目立たせる）。
- 分包方法（カセット／手巻き）：処方箋に印字される「□コ」（コンベア＝手巻き）マークも読み取り、マスタの値と突き合わせる。食い違えば表示して薬剤師に知らせる。
- 一般名・メーカー違いの扱い：処方箋の表記と施設の採用品が違うこと（例：処方箋は「トーワ」、採用は「NP」）が普通にある。照合は **一般名＋規格＋剤形** で行い、マスタの `adopted: true` の製品に置き換えて表示する。置き換えたときは「処方箋：トーワ → 採用品：NP」のバッジを出す。採用品が複数あれば薬剤師に選ばせる。
- 将来構想：全医薬品から作る「親マスタ（外観・出典）」と、施設ごとの「採用・運用マスタ（採用品、区分、分包方法）」を分ける。ハッカソンでは1つのJSONで両方を持ち、構想として説明する。

### 5.4 抽出フロー（Claude活用の見せ場その1）
1. ClaudeがPMDAから添付文書PDFをダウンロード（クラウド環境の `pdfs/` に置く。gitignore）。
2. `npm run extract -- pdfs/xxx.pdf` を実行。ClaudeにPDFを渡し、**JSONスキーマ固定**で外観情報を返させる。読めない項目は `未確認` と答えさせる。根拠の文言（source_quote）も返させる。
3. 出力は `data/drafts/xxx.json`（status: draft）。
4. AKIがCSV（スプレッドシート）で1件ずつ見て、必要なら修正し、`verified` にする。
5. マージして `data/master.json` に反映。
- デモ用は 20〜30 品目：デモ処方の薬＋見た目が似ている白い錠剤。

### 5.5 出典について
- 一次情報としてPMDAの添付文書PDFを使う。URLは改訂で変わることがあるため、`source_revision` と一緒に持ち、リンク切れ時は「PMDAで検索」ボタンに切り替える。

## 6. 処方箋の読み取り（Claude活用の見せ場その2）

### 6.1 入力
- 薬剤欄だけを写した写真1枚。長辺1600px以下にブラウザで縮小。

### 6.2 出力（JSONスキーマ固定）
```json
{
  "items": [
    {
      "name_as_written": "アムロジピン錠5mg「○○」",
      "strength": "5mg",
      "dose_per_time": 1,
      "times_per_day": 1,
      "dose_per_day": 1,
      "timing": ["morning"],
      "days": 14,
      "raw_usage_text": "1日1回 朝食後",
      "confidence": "high"
    }
  ],
  "notes": "読み取れなかった箇所があれば記述"
}
```
- `timing` は `morning / noon / evening` の配列。読み取れなければ空配列（画面2で黄色表示）。
- **服用時点ごとの錠数** `per_timing: {morning: 1, noon: 0, evening: 2}` を必ず出す。「1-0-2 で投与」のような不均等な指示に対応するため。通常は 1回量を各時点に入れる。
- `dosage_form`（`tablet / capsule / other`）と `pack_instruction`（`別包` / `一包化` / 指示なし）を出す。「別包（ヒート包装）」「All One Dose」「○○も含めて一包化」などの指示を拾う。
- 薬品名の括弧内の補足（例：「（通院HD患者は院内処方）」）は `name_note` に分けて、`name_as_written` からは除く。
- 1処方で**複数枚の写真**（2ページ目）を受け付け、まとめて1つの表にする。
- 患者情報が写り込んでいても**出力に含めない**ことをプロンプトで明示する。

### 6.3 マスタ照合
- `name_as_written` を正規化（全角半角、「」内の屋号除去、規格の分離）し、マスタの brand_name / generic_name と照合。
- 一般名処方（「【般】」や一般名表記）は `adopted: true` の製品に置き換える。候補が複数あれば画面2で選ばせる。
- 該当なしは黄色表示＋手で選択（マスタからの検索）。

### 6.4 検算
- `dose_per_time × times_per_day == dose_per_day` と `Σ per_timing == dose_per_day` を確認。不一致は黄色。
- `timing` の要素数と `times_per_day` が合わない場合も黄色。
- 袋ごとの錠数 = Σ（入れる薬の per_timing[その時点]）。袋の見出しに表示。

## 7. 技術構成（Claudeが決定。理由つき）

| 項目 | 選択 | 理由 |
|---|---|---|
| フレームワーク | Next.js（App Router）+ TypeScript | 画面とサーバ側API（キーを隠す場所）を1つのリポジトリで作れる。Claude Codeとの相性がよい |
| UI | Tailwind CSS | スマホ向けのレイアウトを速く作れる |
| 錠剤イラスト | 自前のSVGコンポーネント | 形・色・大きさ・刻印をデータから描ける。画像ファイル不要 |
| Claude API | `@anthropic-ai/sdk`、PDF入力と画像入力、JSON出力 | 抽出と読み取りの両方に使う。モデルは実装時に `claude-api` スキルで最新を確認して選ぶ |
| データ | `data/master.json`（DBなし） | 20〜30件なら十分。公開リポジトリで中身が見える＝透明性にもなる |
| ホスティング | Vercel（無料枠） | HTTPSが自動（スマホカメラに必要）。環境変数でAPIキーを隠せる。GitHub連携で自動デプロイ |
| 認証 | Next.js middleware による共通パスコード＋Cookie | 目的はクレジット保護。最小の実装で足りる |
| コスト保護 | サーバ側で1リクエストの画像サイズ上限、1日あたり呼び出し上限（環境変数） | 万一パスコードが漏れても被害を限定する |
| 開発環境 | Claude Codeのクラウド環境（AKIのPCには何も入れない） | PDF取得・抽出スクリプトもここで実行。APIキーは環境のシークレットに置く |

### 7.1 リポジトリ構成（予定）
```
/app                 画面（Next.js）
/app/api/read-rx     処方箋読み取りAPI（サーバ側でClaudeを呼ぶ）
/components/Tablet   錠剤SVG
/lib                 マスタ照合・検算・類似判定
/scripts/extract.ts  添付文書PDF→draft JSON
/scripts/csv.ts      JSON↔CSV
/data/master.json    マスタ（確認済み）
/data/drafts/        抽出直後（確認前）
/docs                仕様書・計画・デモ台本
/pdfs/               添付文書PDF（gitignore、コミットしない）
```

### 7.2 セキュリティと個人情報
- APIキーは Vercel の環境変数と、ローカルの `.env.local`（gitignore）にのみ置く。画面には出ない。
- 公開URLはパスコードで保護。パスコードは動画・README・コードに書かない。
- 処方箋・1包目の画像はサーバに保存しない。メモリ上で処理して返すだけ。ログに画像や読み取り結果を出さない。
- デモは架空の処方・ダミーの一包化のみ。患者情報・院内データ・病院名は一切使わない。
- `.gitignore`：`.env*`, `pdfs/`, 撮影画像フォルダ。

## 8. 言葉づかいの方針（医療アドバイスにならないために）
- アプリが言ってよいこと：「読み取り値が一致しません」「マスタに該当がありません」「この袋には似た外観の錠剤があります。刻印で区別してください」「添付文書を開く」。
- 言わないこと：「この処方は誤りです」「この用量は多い／少ない」「この薬は一包化に適しません」（施設ルールの初期値は「施設ルールでは別包です」と表現する）。
- 画面下部に常時：「本ツールは監査を支援する情報表示です。判断は薬剤師が行います。」

## 10. デモ処方と検証
- デモ処方：実物の袋に合わせた薬の組み合わせで、日数・数量・並び・別包の品目を変えた**架空の処方箋画像**（紙は使わない）。1患者分に一般名処方の行を混ぜる。白い円形錠を複数含める（似た外観の注意表示が出る構成にする）。
- 実際の処方内容・院内の印刷物は公開リポジトリにも動画にも使わない。
- ダミー一包化：実際の錠剤で作成（職場の許可を得て）。分包紙の印字はなし、または裏側から撮る。
- 検証：わざと誤りを混ぜた1包を用意し、イメージ図を見ながら気づけるかを記録する。
  - ケースA：違う錠剤（見た目も違う）
  - ケースB：似た錠剤（同色・同形・近い大きさ、刻印だけ違う）← 本命
  - ケースC：1錠抜き
  - 記録：気づけたか／何秒か／どの情報（刻印・大きさ・錠数）で気づいたか

## 11. 審査基準との対応

| 基準 | 本作品での対応 |
|---|---|
| インパクト 30% | 見逃すと危害最大のミス（似た見た目の違う薬）に、どの施設でもスマホで対応できる。新人・応援の監査の質を底上げ |
| デモ 25% | 「この1包、処方どおりだと言い切れますか？」から始め、イメージ図で白い錠剤が判別できる瞬間を見せる |
| Claudeの活用 25% | ①添付文書PDF→外観マスタ抽出（人の確認つき）②処方箋写真→構造化＋検算 ③開発自体をClaude Codeで（コミット履歴） |
| 深さと実行 20% | ベテランの手順をそのまま画面化。「なし／未確認」の区別、カセット／手巻き、一般名→採用品、言葉づかいの方針など現場の細部 |

## 12. 決定事項と未決事項

### 決定（11/2 夜、AKIの回答）
| 項目 | 決定 | 補足 |
|---|---|---|
| 処方箋の用法表記 | 「1日3錠 分3 毎食後」の1日量形式を主に対応 | 1回量形式も読めるようにはするが、精度試験は1日量形式で行う |
| 袋の区分 | 朝・昼・夕の3つ | デモは3患者分（①朝昼夕 ②朝夕 ③朝夕）。眠前は対象外と明記 |
| 薬剤名の書き方 | 商品名を基本に、1患者分だけ一般名処方を混ぜる（推奨E2） | 病院の現実は商品名のみ。薬局への展開を見据えて「一般名→採用品の置き換え」を1回だけ見せる |
| イメージ図の並び順 | **処方箋の記載順**（G2） | 監査は処方箋を上から見ていくため。各行から添付文書を開ける。「大きさ順」への切り替えは余裕があれば |
| 似た外観の注意表示 | 並び順に関係なく、同じ袋内の似た組を同じ色のバッジで結びつける | 隣り合っていなくても分かるようにする |
| 分包方法の見せ方 | 情報カードの中だけに表示（H1） | 作りながら再検討 |
| マスタ確認の方法 | CSVをスプレッドシートで確認・修正（I1） | ブラウザの確認画面は作らない |
| 刻印の扱い | 社名マークだけ＝「なし」＋補足欄に記載。数字や文字があれば刻印として扱う（J1） | 例：n753 のような識別コードは刻印 |
| 開発環境 | AKIのPCには何も入れない。開発はClaude Codeのクラウド環境、公開はVercel（ブラウザ操作のみ） | APIキーはクラウド環境のシークレットとVercelの環境変数にだけ置く |
| 添付文書PDFの取得 | Claudeがクラウド環境から取得（F3）。PMDAへの通信許可が必要 | 取得したPDFはコミットしない |
